# PDF RAG System

一个用于**学习 RAG（Retrieval-Augmented Generation）全链路**的 PDF 问答系统。

从 PDF 加载 → 文本切分 → 向量化 → 向量检索 → 调用 LLM 生成答案，每一步都拆成独立模块，
便于逐环节替换、做对照实验。目标不是「能跑」，而是**能说清每个环节为什么这么设计**。

## 环境准备

1. 安装依赖：

   ```bash
   pip install -r requirements.txt
   ```

   若需要 GPU 版 PyTorch（推荐，向量化显著更快），改用：

   ```bash
   pip install -r requirements_torch_cuda.txt
   ```

2. 配置环境变量：复制 `.env.example` 为 `.env`，填入 DeepSeek API Key。

   ```
   DEEPSEEK_API_KEY=sk-xxxxxxxx
   DEEPSEEK_MODEL=deepseek-chat
   DEEPSEEK_API_BASE=https://api.deepseek.com
   LOG_LEVEL=INFO
   ```

   > `.env` 已被 `.gitignore` 忽略，**不要提交到仓库**。

3. 准备 embedding 模型（首次运行需要）：

   默认使用中文模型 `BAAI/bge-small-zh-v1.5`，放在 `models/bge-small-zh-v1.5/`。

   ```bash
   python -c "
   import os
   os.environ['HF_ENDPOINT'] = 'https://hf-mirror.com'
   from huggingface_hub import snapshot_download
   snapshot_download(
       repo_id='BAAI/bge-small-zh-v1.5',
       local_dir='models/bge-small-zh-v1.5',
       allow_patterns=['*.json', '*.txt', '*.safetensors'],
   )
   "
   ```

   > 国内网络无法直连 `huggingface.co`，需走镜像站 `hf-mirror.com`（`config.py` 已默认设置）。
   > 用 `allow_patterns` 跳过冗余的 `pytorch_model.bin`，下载量从 183MB 降到 92MB。
   > 也可直接指定 HuggingFace 模型名，例如 `EMBEDDING_MODEL=BAAI/bge-m3`（会自动走镜像下载）。

4. 准备精排模型（**可选**，只有用 `--rerank` 或 `RERANK_ENABLED=1` 时才需要，约 1.1GB）：

   ```bash
   python -c "
   import os
   os.environ['HF_ENDPOINT'] = 'https://hf-mirror.com'
   from huggingface_hub import snapshot_download
   snapshot_download(
       repo_id='BAAI/bge-reranker-base',
       local_dir='models/bge-reranker-base',
       allow_patterns=['*.json', '*.txt', '*.model', '*.safetensors'],
       ignore_patterns=['*.onnx', '*.h5', 'pytorch_model.bin'],
   )
   "
   ```

   > 不装也能跑：默认 `RERANK_ENABLED=0`，混合检索（向量 + BM25 + RRF）不依赖它。

5. 准备语料（不入库，需自行下载）：

   ```bash
   python scripts/download_corpus.py            # GitHub 直连
   python scripts/download_corpus.py --mirror   # 走 ghproxy 镜像（直连慢时用）
   ```

   会拉取 3 篇中文 PDF（约 36MB，合计 719 页）：

   | 文件 | 来源 | 特点 |
   | --- | --- | --- |
   | `llm-universe.pdf` | Datawhale《动手学大模型应用开发》 | 与大模型应用 / RAG 直接相关 |
   | `pumpkin-book.pdf` | Datawhale《南瓜书：机器学习公式详解》 | XeLaTeX 排版，公式密集 |
   | `ml-notes-ng.pdf` | 吴恩达机器学习课程中文笔记 | Word 排版 |

   也可以直接把自己的 PDF 放进 `data/pdfs/`。

## 使用方法

```bash
# 单次提问（默认走增量：只索引新增/变动的 PDF）
python main.py --query "什么是 RAG？"

# 只同步索引、不提问
python main.py --reindex

# 丢弃全部索引并重建（更换 embedding 模型或切分参数后必须执行）
python main.py --recreate --query "什么是 RAG？"
python main.py --recreate --reindex

# 进入交互模式
python main.py --chat

# 检索质量评测（Hit@1 / Hit@k / MRR）
python eval/run_eval.py --detail --save results/eval.json

# 对比不同检索后端 / 索引类型（同一批题、同一套判定）
python eval/run_eval.py --backend brute
python eval/run_eval.py --backend faiss --faiss-index-type hnsw

# 对比四种检索策略（S4：单变量对照）
python eval/run_eval.py --retriever vector            # 纯向量（S3 基线）
python eval/run_eval.py --retriever bm25              # 纯 BM25
python eval/run_eval.py --retriever hybrid            # 向量 + BM25 + RRF
python eval/run_eval.py --retriever hybrid --rerank   # 再加 Cross-Encoder 精排

# 换第二套判定口径（LLM-as-Judge，需 API key；判定结果会缓存到 results/）
python eval/run_eval.py --retriever hybrid --judge

# 参数敏感性
python eval/run_eval.py --retriever hybrid --rrf-k 10
python eval/run_eval.py --retriever hybrid --rrf-weight "1,2"    # vector:1, bm25:2
python eval/run_eval.py --retriever hybrid --candidate-k 10

# ANN 规模实验：暴力 vs FAISS(flat/hnsw/ivf) 的延迟与 Recall@k
python scripts/benchmark_ann.py --mode synth --out results/ann_benchmark_synth.json
python scripts/benchmark_ann.py --mode corpus --real-queries

# 分层题库（S5）：单事实 / 同领域干扰 / 跨文档多跳 / 无答案
python scripts/check_questions.py                                    # 先自检题库
python eval/run_eval.py --questions eval/questions_v2.json --retriever hybrid
python eval/run_eval.py --questions eval/questions_v2.json --retriever hybrid --top-k 12

# 生成层评测（引用 / 忠实度 / 拒答），需 API key
python eval/run_gen_eval.py --questions eval/questions_v2.json --judge
python eval/run_gen_eval.py --questions eval/questions_v2.json --top-k 12 --judge

# prompt 消融：去掉拒答条款 / 去掉引用要求（用于证明约束确实起作用）
python eval/run_gen_eval.py --questions eval/questions_v2.json --prompt-variant no_refusal --judge
python eval/run_gen_eval.py --questions eval/questions_v2.json --prompt-variant no_cite --judge
```

问答时也可以直接切检索策略：

```bash
python main.py --query "什么是 RAG？" --retriever hybrid --rerank
python main.py --query "什么是 RAG？" --no-rerank
```

未配置 `DEEPSEEK_API_KEY` 时，程序仍可运行**检索部分**，只是不调用 LLM 生成答案。

> 本机推荐解释器：`D:\anaconda\python.exe`（依赖齐全且 GPU 可用）。

### Web 前端（本机可视化）

```bash
# 前提：索引已建好（python main.py --reindex）
D:\anaconda\python.exe server/app.py
# 浏览器打开 http://127.0.0.1:8000
```

Windows 上也可以直接双击仓库根目录的 **`start_server.bat`**：它会设好
`HF_HUB_OFFLINE=1`、用 `D:\anaconda\python.exe` 启动，并保持一个独立控制台窗口。
（脚本里的 `set PYTHON=` 一行可改成自己的解释器路径。）

> **为什么需要这个 .bat**：进程的生命周期跟着启动它的那个终端走。从编辑器/CI 的
> 后台 shell 里启动，会话一结束进程就被回收，表现就是「昨天还好好的，今天 8000 端口
> 没人监听」——这不是代码坏了。判断方法：`GET /api/status` 连不上 + 没有 python
> 进程 = 进程没了，重启即可；如果是 500 或返回异常字段，才是代码问题。

页面能做的三件事，对应三个接口：

| 接口 | 前端上的位置 | 作用 |
| --- | --- | --- |
| `GET /api/status` | 顶栏徽章 + 左栏语料 | 索引真实状态（块数 / 维度 / 后端 / 每本文档的页数与块数） |
| `POST /api/chat` | 问答页 | SSE 流式：先推来源，再逐 token 推答案，最后推引用校验结果 |
| `POST /api/search` | 检索调试页 | 只检索不生成，**逐块显示 V# / B# / RRF / 精排分** |

**前端想说明的两件事**（不只是「有个界面」）：

1. **引用是可点的、可校验的**。答案里的每个 `[来源: 文件 第N页]` 会渲染成标签，
   点一下跳到对应来源卡片；如果那一页根本不在本次召回里，标签会被标红划掉 ——
   **编造引用当场就能看见**，不需要人肉对数。
2. **拒答时仍然显示召回块**。拒答卡片下面留着「召回了 4 块，但没有一块足以支撑答案」，
   这样「是没检索到」还是「检索到了但不相关」一眼可分 —— 和实验 8 的排查路径一致。

**几个刻意的工程取舍**：

- **不引入 `sse-starlette`**：SSE 就是一个不结束的 HTTP 响应，`StreamingResponse` 足够，
  少一个依赖少一处版本冲突。
- **精排模型必须进程级单例**：`create_hybrid_retriever(rerank=True)` 每次都会新建一个
  1.1GB 的 Cross-Encoder。CLI 里进程一退就回收，常驻服务里就是内存灾难 + 每次改配置卡十几秒。
- **检索器按配置缓存**：`HybridRetriever.__init__` 会立即构建 BM25 倒排索引（1857 块约 1s），
  前端每拖一次滑块都重建是不可接受的。
- ⚠️ **踩过一个真 bug：锁里做慢操作 + 嵌套不可重入锁 = 死锁**。
  最初 `_get_retriever()` 整个包在 `with _LOCK:` 里，内部又调 `_get_reranker()`，
  而后者也要拿同一把 `threading.Lock` —— 请求永远不返回，日志停在「BM25 索引就绪」，
  没有异常、没有超时提示。修法两层：**慢操作挪出锁外**（持锁 10 秒等于让所有请求排队）
  + **锁外查一次、锁内再查一次**（双重检查）。通用规则：**不要在锁里做 I/O 或加载模型**。

### 可调参数（环境变量覆盖，便于做对照实验）

| 变量 | 默认值 | 说明 |
| --- | --- | --- |
| `EMBEDDING_MODEL` | `models/bge-small-zh-v1.5` | 可填 HuggingFace 模型名 |
| `CHUNK_UNIT` | `token` | `token` 按模型 token 数切分；`char` 按字符数 |
| `CHUNK_SIZE` | `384` | 切分块大小（单位见上） |
| `CHUNK_OVERLAP` | `80` | 相邻块重叠大小 |
| `CHUNK_NORMALIZE` | `0` | 是否把 PDF 物理行合并为语义段落（实测无收益，默认关） |
| `VECTOR_BACKEND` | `faiss` | 检索后端：`brute`（手写暴力，精确）或 `faiss` |
| `INGEST_NORMALIZE` | `1` | 入库时是否做 L2 归一化（归一化后余弦 == 内积） |
| `RETRIEVAL_TOP_K` | `4` | 召回条数 |
| `RETRIEVAL_SCORE_THRESHOLD` | 空（不过滤） | 相似度阈值；填数字则丢弃低于它的结果，填 `none`/`off` 关闭 |
| `FAISS_INDEX_TYPE` | `hnsw` | `flat` / `hnsw` / `ivf` |
| `FAISS_M` | `32` | HNSW 每节点连接数 |
| `FAISS_EF_CONSTRUCTION` | `200` | HNSW 建索引候选池 |
| `FAISS_EF_SEARCH` | `64` | HNSW 查询候选池（运行时参数，调大更准更慢） |
| `FAISS_NLIST` | `256` | IVF 聚类簇数 |
| `FAISS_NPROBE` | `8` | IVF 查询时搜索的簇数 |
| `RETRIEVAL_MODE` | `hybrid` | 召回通道：`vector` / `bm25` / `hybrid`（双通道 + RRF） |
| `RETRIEVAL_CANDIDATE_K` | `50` | 每路召回候选数（必须远大于 `RETRIEVAL_TOP_K`） |
| `RRF_K` | `60` | RRF 平滑常数；越小头部优势越大 |
| `RERANK_ENABLED` | `0` | 是否启用 Cross-Encoder 精排 |
| `RERANKER_MODEL` | `models/bge-reranker-base` | 精排模型路径 |

> **阈值必须随模型重新标定**：`RETRIEVAL_SCORE_THRESHOLD` 的含义取决于 embedding 模型的分数分布
> （bge 和 MiniLM 的尺度完全不同），照抄别人的阈值是没有意义的。

## 设计说明

- **为什么自己写了一遍暴力检索，又保留它？**
  手写一遍才能真正理解 **ANN 在解决什么问题**——暴力检索是 O(n·d)，数据量上来后延迟线性增长。
  保留它有三个用处：① ANN 的 Recall@k 需要一个「真值」来对照；② 它精确，是正确性基线；
  ③ 几千个块时它其实已经够快，能提示「不要过早优化」。见实验 6。
- **为什么用 FAISS 而不是 Chroma？**
  FAISS 是纯索引库，没有额外的元数据存储与服务层，索引参数（M / efSearch / nlist / nprobe）
  全部显式暴露——学习索引原理时干扰最小。跑通后再换 Chroma / Qdrant 只是接口替换。
- **为什么索引和向量分开存？**
  `embeddings.npy` 与索引文件分开，换来两个好处：换后端（brute ↔ FAISS）、换索引类型
  （flat ↔ hnsw ↔ ivf）都**不需要重新 embedding**，直接从向量重建即可。
- **为什么用 pypdfium2 抽 PDF，而不是 langchain 默认的 PyPDFLoader？**
  实测中文 PDF 抽取失败，见实验 3。
- **为什么切分按 token 而不是按字符？**
  embedding 模型的输入上限是按 token 算的，按字符切会让中文块超限被静默截断，见实验 4。
- **为什么向量检索之外还要加 BM25？**
  两者的**错误模式不同**：向量把罕见词「平均」掉，BM25 遇到改写就零分。
  失败集合交集不大，取并集才有收益。但注意实验 7 的结果：在当前的 20 题集上，
  混合检索**没有**在 Hit@1 上打败纯向量——加进来是因为它提供了另一种错误模式，
  而不是因为它让指标更好看。
- **为什么用 RRF 融合而不是加权分数和？**
  余弦分数 ∈ [-1,1]、BM25 无上界，直接相加会被量纲大的一方支配，权重也失去意义。
  RRF 只看名次，跨模型/跨语料不用重新调参。代价是丢掉分数差距信息，
  因此它只做融合，排序精度交给精排。
- **为什么精排不直接用在全库上？**
  Cross-Encoder 要把 `[query, doc]` 拼起来过一次完整前向，**无法预计算**。
  50 个候选实测 625 ms；全库 1857 个候选就是 20 秒以上。
  所以是两段式：Bi-Encoder 召回（快、粗、可预计算）→ Cross-Encoder 精排（慢、准、候选少）。
- **为什么 prompt 要抽成模块并带版本号？**
  写在 f-string 里的 prompt 一改就没了，评测结果无法归因到具体 prompt。
  抽出来 + 版本号后，「v1-norefuse 的过度拒答是 11.6%」这种结论才有意义。
  改 prompt 必须改版本号，否则缓存会复用旧口径的判定（S4 踩过）。
- **为什么拒答要分「哨兵」和「人话」两套？**
  机器需要**可判定**（`INSUFFICIENT_CONTEXT` 一次字符串匹配），
  人需要**可读**（"资料中没有找到足够的信息…"）。混用会导致：用自然语言判断时，
  模型改写句子就漏判；用哨兵展示时，用户看到一行错误码。
  但实测（实验 8）发现：哨兵条款对「该拒就拒」没有贡献，只提高了过度拒答，
  所以它只在对下游系统有严格机器可读要求时才值得引入。
- **为什么引用校验不用 LLM？**
  `[来源: 文件 第N页]` 是否落在本次召回块里，是确定性问题，正则 + 集合比对即可。
  用模型判断只会把可复现的检查变成有随机性的检查。
- **为什么检索指标和生成指标要分开报？**
  两者会互相掩盖：检索没给到和模型不敢答，在「答案对不对」这一层看起来一模一样。
  分开报之后，实验 8 才能得出「过度拒答 23%→16% 来自 top_k 从 4 到 12」这种可行动的结论。
- **`use_reranker` 为什么从 `RAGPipeline` 里删掉了？**
  它原本是「声明了但从未生效的参数」。根因不是没实现，而是**放错了层**：
  检索策略应由检索层决定，`RAGPipeline` 只负责组装 context 和调 LLM。
  挪到 `HybridRetriever(reranker=...)` 之后，做检索 A/B 完全不用碰生成代码。
- **embedding 模型**：`BAAI/bge-small-zh-v1.5`（512 维，中文）。取代了最初的
  `all-MiniLM-L6-v2`——后者是纯英文模型，见实验 1。

## 评测方法（`eval/`）

`eval/questions.json` 是 20 道固定问题（覆盖 3 篇文档）。`eval/run_eval.py`
**直接调用线上检索路径**（`create_hybrid_retriever`，与 `main.py` 同一个工厂）并统计：

| 指标 | 含义 |
| --- | --- |
| Hit@1 | 排第一的块是否被判定为「包含答案」 |
| Hit@k | 前 k 个块里是否有被判定为「包含答案」的 |
| MRR | 首个命中块排名的倒数平均值（第 1 位 = 1.0） |

**两套判定口径**，这是 S4 学到的关键一课（见实验 7）：

| 口径 | 做法 | 特点 |
| --- | --- | --- |
| 关键词（默认） | 块里是否出现 `expected_keywords` 中任一词 | 便宜、确定、可复现；但**系统性偏袒字面匹配** |
| 语义（`--judge`） | LLM 判断「这块能否为回答问题提供有用信息」 | 不受用词影响；但慢、要钱、结果需缓存 |

```bash
python eval/run_eval.py --retriever hybrid            # 关键词口径
python eval/run_eval.py --retriever hybrid --judge     # 语义口径
```

> **注意默认值有意不一致**：`main.py` 的默认检索模式是 `RETRIEVAL_MODE=hybrid`（线上要好效果），
> 而 `eval/run_eval.py` 的 `--retriever` 默认是 `vector`（评测要固定基线口径，与 S2/S3 的历史数字可比）。
> 这不是 bug —— **评测默认值一旦跟着线上变，历史数据就失去可比性**。

**为什么必须两套**：实测同一批检索结果，换判定器后 `vector` 的 Hit@1 从 0.60 变 0.90，
而算法之间的差距几乎消失。**只跑一套口径，你测到的是判定器，不是检索方法。**

做 chunk 策略对照实验时请固定 `--backend brute`（精确检索 = 真值），
这样与历史数字同口径；比较向量库/索引类型时才切换后端。

### v2 题库与生成层评测（S5）

`eval/questions.json`（20 题）保留作 S2–S4 的历史基线，**不再扩充**——换题库会让历史数字失去可比性。
S5 另起 `eval/questions_v2.json`（50 题，按失败模式分层），配套三件事：

```bash
python scripts/check_questions.py                                  # ① 题库静态自检
python eval/run_eval.py --questions eval/questions_v2.json --retriever hybrid --top-k 4    # ② 检索层
python eval/run_gen_eval.py --judge --top-k 4                      # ③ 生成层（需 API key）
python eval/run_gen_eval.py --judge --prompt-variant no_refusal \
       --save results/gen_eval_no_refusal.json                     # ④ prompt 消融
```

| 脚本 | 测什么 | 判定方式 |
| --- | --- | --- |
| `run_eval.py` | Hit@1 / Hit@k / MRR + **来源命中率**（干扰层）/ **来源覆盖率**（多跳层） | 关键词 或 LLM（`--judge`） |
| `run_gen_eval.py` | 引用覆盖率 / 合法率 / 编造数、忠实度、拒答双比率、多来源引用率 | 引用校验**纯代码**；忠实度用 LLM；拒答用 `refusal_state()` |
| `check_questions.py` | 题库自身是否自洽（标注来源里真有答案） | 静态匹配，不调模型 |

> 拒答判定**不复用 pipeline 返回的 `refused`**：那是哨兵匹配的结果，做 prompt 消融时哨兵会消失。
> 评测侧必须用一套与 prompt 无关的判定，否则「拒答率 0%」分不清是模型没拒还是工具失明（实验 8）。

**这个指标的边界（必须说清楚）**：
- 关键词命中是 Hit Rate 的**廉价代理**，不是人工标注的「标准答案块」。
  实测它会产生假阴性（正确块没有原样出现关键词），见实验 7。
- 关键词覆盖率事先统计过（避免出现太普遍的词导致指标失去区分度），但**题目之间难度并不均一**。
- 语义判定同样不是真值：judge 会被同形异义骗（问「线性判别分析 LDA」时它把
  「LDA 主题模型」判成相关），也会受长度偏差影响。
- 因此两套口径都**只能用于同一批题、同一判定下的横向比较**，不能当作绝对分数或对外宣称「准确率」。
- **当前 Hit@4 在语义口径下已饱和到 1.00**，意味着这批题已经区分不出检索方法的优劣。

## 实验记录

> 原则：**一次只改一个变量**，其余条件完全相同，改完用同一组问题对比前后结果。

### 实验 1 · 英文 embedding → 中文 embedding（S1）

**背景**：项目最初中文提问经常答不出，第一反应容易去调 prompt，但无效。

**假设**：根因不在 LLM，而在**检索**——`all-MiniLM-L6-v2` 是纯英文模型（384 维），
编码中文时语义空间塌陷，几乎所有中文句子的向量都挤在一起，检索接近随机。

**方法**：单变量对照。同一份文档、同一套代码，只切换 `EMBEDDING_MODEL` 后重建索引。

| 问题 | `all-MiniLM-L6-v2`（384维） | `bge-small-zh-v1.5`（512维） |
| --- | --- | --- |
| RAG 有哪些好处？ | 召回 **1** 块，且不含答案 → LLM 拒答 | 召回 **2** 块 → **正确答出全部 4 条好处** |
| RAG 是怎么工作的？ | 召回 1 块，能答（答案恰好在第 1 块） | 召回 2 块，能答 |

**补充证据（文本层面，不依赖语料规模）**：
对同一组中文句子做两两余弦相似度，比较「相关句对」与「无关句对」的分数差：

| 句对 | `all-MiniLM-L6-v2` | `bge-small-zh-v1.5` |
| --- | --- | --- |
| 「RAG 有哪些好处？」 ↔「RAG 的优点是更新及时、减少幻觉」（相关） | 0.688 | 0.706 |
| 「RAG 有哪些好处？」 ↔「今天天气不错」（无关） | **0.545** | **0.303** |
| **区分度（相关 − 无关）** | **0.143** | **0.403** |

英文模型给毫不相关的中文句子打了 0.545 的高分——**这正是中文检索失效的直接证据**：
无关内容也能拿到不低的相似度，排序自然失去意义。换模型后区分度提升到约 2.8 倍。

**结论**：RAG 效果差时，**先怀疑检索，不要习惯性甩锅给 LLM**。

**代价与注意**：
- 向量维度 384 → 512，**必须重建索引**（`python main.py --recreate`），旧索引不兼容
- 模型体积 92MB，CPU 也能跑；本项目在 GPU（RTX 4060）上编码

### 实验 3 · PDF 解析器选型（S2）

**现象**：`pumpkin-book.pdf` 用原来的 `PyPDFLoader` 抽出来**全是乱码**，汉字占比 0.0%。

**排查**：用 4 个解析器抽同一份文件（196 页）：

| 解析器 | 抽取字符数 | 汉字占比 | 耗时 |
| --- | --- | --- | --- |
| `pypdf`（原 `PyPDFLoader` 的底层） | 209,834 | **0.0%（乱码）** | 8.2s |
| `pdfminer` | 330,183 | 27.4% | 33.7s |
| `pdfplumber` | 312,030 | 29.0% | 32.8s |
| **`pypdfium2`（现用）** | 328,715 | **27.6%** | **2.5s** |

**根因**：该 PDF 由 XeLaTeX（`xdvipdfmx`）生成，内嵌的字体子集缺少 ToUnicode 映射，
文字能不能抽出来取决于解析器的兜底策略。对比另两份：Word 排版的 `ml-notes-ng.pdf`
三种解析器都能抽（≈48%），说明**问题不在「中文 PDF」本身，而在「特定生成方式 × 特定解析器」的组合**。

**为什么这个坑危险**：抽取失败**不报错**，只是把乱码默默喂给 embedding，检索静默失效。
因此 loader 里加了空页告警（扫描版 PDF 会触发，提示需要 OCR）。

**结论**：文档加载层要当作有质量风险的一环来验证——**先抽样打印，再谈建模**。

### 实验 4 · 切分单位：字符 → token（S2，关键修正）

**问题**：`bge-small-zh-v1.5` 输入上限 **512 token**，而 `chunk_size=1000` 是**字符数**。
中文约 1 字 ≈ 1 token，英文约 3.5 字 ≈ 1 token——所以「1000 字符」对英文安全，对中文必然超限。

切分后加了自检，基线索引立刻报出来：

```
chunk token 分布: min=15 median=492 max=950 (embedding 模型上限 512)
530/1142 chunk(s) 超出 embedding 模型上限 512 tokens (最大 950)，超出部分会被静默截断丢弃
```

**46.4% 的块超限，最大 950 token**——意味着这些块的后半段根本没进向量库。

**方法**：单变量对照，只改切分单位（其余：同一解析器、同一模型、同一批语料、同一组 20 题）。

| 配置 | 块数 | chunk token（中位/最大） | 超限块数 | Hit@1 | Hit@4 | MRR |
| --- | --- | --- | --- | --- | --- | --- |
| `char` 1000 / 200 | 1142 | 492 / **950** | **530（46.4%）** | 0.450 | 0.600 | 0.517 |
| **`token` 384 / 80** | 1860 | 357 / 386 | **0** | **0.600** | **0.700** | **0.642** |

**结论**：Hit@1 +0.150、Hit@4 +0.100、MRR +0.125。切分单位必须与 embedding 模型的计数方式对齐。

> 顺带一提：本次同时把分隔符从默认的 `["\n\n","\n"," ",""]` 换成了中文友好的
> `["\n\n","\n","。","！","？","；","：","，"," ",""]`（中文几乎不用空格，默认分隔符
> 会把切点落在任意位置）。这一项与解析器修复一起发生在基线测量之前，**未单独度量**，
> 严格来说这笔账还挂着——见「已知限制」。

### 实验 5 · 段落规整（失败，默认关闭）

**假设**：PDF 里的换行是排版产物（为了塞进页宽），不是语义边界，合并成段落后切分质量应该更好。

**方法**：单变量，在 `token 384 / 80` 基础上打开 `CHUNK_NORMALIZE`。

| 配置 | 块数 | Hit@1 | Hit@4 | MRR |
| --- | --- | --- | --- | --- |
| `token` 384 / 80（对照） | 1860 | **0.600** | **0.700** | **0.642** |
| + 段落规整（首版） | 1929 | 0.550 | 0.700 | 0.604 |
| + 段落规整（加行长度门槛后重试） | 1926 | 0.550 | 0.700 | 0.617 |

**两个版本都没有跑赢对照，指标反而下降。**

**原因分析**：合并物理行时，**小标题会被并进上一段**，等于亲手毁掉了 `\n\n` 这个
优先级最高的分隔符——本来「标题 / 正文」是天然的语义边界，合并后切点变得随机。
第二版加了「只合并较长正文行」的门槛，回升一点但仍不达标。

**结论**：这是个**负面结果**，但它很有价值——「看起来更干净」的文本预处理不一定更好，
**必须用指标说话**。代码和开关都保留（`CHUNK_NORMALIZE=1` 可复现），默认关闭。

### 实验 6 · 向量库工程化：暴力检索 vs FAISS（S3）

**先厘清一件事：当前规模根本用不上 ANN。**
1857 个块 / 512 维，暴力检索一次查询 **0.06ms**。所以 S3 的目的不是「提速」，而是三件事：

1. **把检索实现做对**：入库 L2 归一化、top-k 与阈值分层、argpartition 取 top-k；
2. **亲手量出 ANN 的代价**——「近似」到底损失了多少召回率，这个数字只有自己写一遍暴力检索才拿得到；
3. **补上增量索引与去重**——这才是真实工程里天天用到、而 demo 里通常没有的东西。

#### 改动清单

| 改动 | 说明 |
| --- | --- |
| 入库 L2 归一化 | 归一化后 余弦 == 内积，检索省掉每次重算全库范数；分数落入 [-1,1] 才谈得上「阈值」 |
| top-k 与阈值分层 | 删除硬编码 `> 0.1`。top-k 决定「喂几块」，阈值决定「够不够格」，后者改为配置项、默认不过滤 |
| `argpartition` 取 top-k | 只要前 k 个却对全库做 O(n log n) 全排序是浪费 |
| 新增 FAISS 后端 | `flat`（精确对照）/ `hnsw`（`M` / `efConstruction` / `efSearch`）/ `ivf`（`nlist` / `nprobe`） |
| 内容 hash 去重 | 按 chunk 内容 sha1 去重（实测立刻剔掉 3 个重复块：1860 → 1857） |
| 增量索引 | 按 PDF 内容指纹只处理新增/变动的文件，不再每次全量重建 |
| 索引与向量分离存储 | `embeddings.npy` + 索引文件分开 → 换后端/换索引类型**不必重新 embedding** |

#### (a) 检索指标对照（20 题，同一语料、同一模型、同一口径）

| 检索后端 | 块数 | Hit@1 | Hit@4 | MRR |
| --- | --- | --- | --- | --- |
| brute（手写暴力余弦） | 1857 | 0.6000 | 0.7000 | 0.6417 |
| faiss `flat`（精确） | 1857 | 0.6000 | 0.7000 | 0.6417 |
| faiss `hnsw`（M=32, efSearch=64） | 1857 | 0.6000 | 0.7000 | 0.6417 |
| faiss `ivf`（nlist=256, nprobe=8） | 1857 | 0.5500 | 0.6500 | 0.5917 |

**三条结论**：
1. **归一化 + 阈值分层 + argpartition 这一通改造没有掉指标** —— 与 S2 基线完全一致，说明改的是实现而不是行为。
2. **1857 个块上 HNSW 与暴力检索结果完全相同**（近似索引在这个规模几乎无损），也再次说明这个规模不需要 ANN。
3. **IVF 反而掉了一题**（q13「特征缩放和均值归一化怎么做」）。原因不是 bug：
   `nlist=256` 对 1857 个向量来说**过大**——平均每簇只有约 7 个向量，
   `nprobe=8` 一次只看 8 个簇、即约 56 个候选，真答案很可能不在里面。
   IVF 的经验公式是 `nlist ≈ √n`（这里是 ~43）。**这是「索引参数必须与数据规模匹配」的直接证据。**

#### (b) 规模实验：延迟 vs 召回率

当前语料太小（1.9k），看不出 ANN 的意义，所以做了规模放大实验
（`scripts/benchmark_ann.py`，20 条查询，k=4，以暴力检索结果为 Recall 的真值）：

**真实向量分布**（把真实语料向量复制到目标规模并加小幅噪声，用 20 个真实问题作查询）：

| 语料规模 | 暴力检索 | HNSW efSearch=64 | HNSW efSearch=256 | IVF nprobe=8 | IVF nprobe=32 |
| --- | --- | --- | --- | --- | --- |
| 2,000 | 0.063 ms (1.000) | 0.035 (0.988) | 0.078 (1.000) | 0.010 (0.675) | 0.031 (0.925) |
| 20,000 | 0.602 ms (1.000) | 0.151 (0.950) | 0.434 (1.000) | 0.024 (0.813) | 0.093 (0.963) |
| 100,000 | 2.381 ms (1.000) | 0.220 (0.875) | 0.689 (0.950) | 0.180 (0.738) | 0.681 (0.863) |
| 200,000 | 4.419 ms (1.000) | **0.240 (0.838)** | **0.722 (0.950)** | 0.365 (0.813) | 1.621 (0.950) |

> 格子格式：**单次查询延迟（Recall@4）**。`faiss flat` 在所有规模下与暴力检索一致（1.000），
> 故未单列。完整原始数据见 `results/ann_benchmark_corpus.json`。

**在 200k 规模上**：HNSW（efSearch=64）比暴力检索**快 18.4 倍**，代价是 Recall@4 从 1.000 降到 0.838；
把 `efSearch` 提到 256 能拿回 0.950，而延迟仍然快 **6.1 倍**。
**「准 / 快」是同一个索引上的运行时旋钮**——这是 HNSW 最实用的性质。

#### (c) 一个反直觉的负面发现：合成数据上 ANN 会崩

同样流程换成**归一化高斯随机向量**（ANN 领域的标准微基准）：

| 语料规模 | 暴力检索 | HNSW efSearch=16 | HNSW efSearch=256 | IVF nprobe=32 |
| --- | --- | --- | --- | --- |
| 200,000 | 4.978 ms (1.000) | 0.172 (**0.038**) | 1.581 (**0.250**) | 1.198 (**0.350**) |

召回率**断崖式下跌**。这不是索引实现有问题，而是**维度灾难**：
在 512 维近似均匀分布的数据里，最近邻与第 200 名的距离差被压缩到几乎没有，
任何剪枝都会丢掉真正的 top-k。这也是为什么公开的 ANN 基准集
（SIFT1M / GIST1M / GloVe）用的都是**真实数据**而不是随机数。

**两组合成 / 真实的对比说明**：
- 真实分布的 Recall（表格 b）偏乐观——数据由真实向量复制加噪而来，相似度整体偏高；
- 合成分布（表格 c）是偏悲观的下界；
- **真实场景落在两者之间，而「落在哪里」取决于数据的固有维度**。
  所以不要拿别人的 ANN 召回率数字去承诺线上指标，必须用**自己的**数据测。

#### 踩坑记录（都是 Windows 环境特有的）

1. **`faiss-cpu` 版本必须锁 1.7.4。** 1.8.0 / 1.15.1 上 `IndexHNSWFlat.add()` 直接**段错误**
   （无异常、无堆栈，进程直接死）。根因是 OpenMP 运行时 DLL 冲突：Anaconda 的 MKL 带
   `libiomp5md.dll`，faiss 的 wheel 又自带一份 OpenMP，两者同时加载即崩。
   设 `KMP_DUPLICATE_LIB_OK=TRUE` 能让 `flat`/`ivf` 跑起来，但 HNSW 仍然崩；换 1.7.4 后全部正常。
   **教训：段错误 ≠ 代码错，先怀疑二进制依赖冲突。**
2. **`faiss.write_index` 在非 ASCII 路径下会失败**：
   `Error: 'f' failed: could not open D:\代码\PDF-ptokect\...\faiss.index for writing`。
   原因是它内部用的是 C++ 的 `fopen`，不认 Unicode 路径。
   解法：改用 `faiss.serialize_index()` 只用内存序列化，落盘交给 Python 的 `open()`。

### 实验 7 · 混合检索 + 精排（S4）—— 以及一次被指标骗到的经历

这是本项目到目前为止**最有价值的一次实验**，因为它的结论不是「我的新方法更好」，
而是「**我的评测方法把结论带偏了**」。

#### 改动清单

| 改动 | 说明 |
| --- | --- |
| 自研 BM25 | `src/bm25.py`，零第三方依赖。倒排表 + IDF + 词频饱和 + 长度归一化 |
| 中文分词 | BM25 是词袋模型，中文不分词就等于把整段文本当一个「词」，直接失效 |
| RRF 融合 | `src/hybrid_retriever.py`，只看名次不看分数，对分数尺度免疫 |
| Cross-Encoder 精排 | `src/reranker.py`，`bge-reranker-base`，只对融合后的候选打分 |
| 统一组装入口 | `create_hybrid_retriever` 同时被 `main.py` 与 `eval/` 调用 |
| 第二套判定口径 | `eval/judge.py`，LLM-as-Judge + 磁盘缓存 |
| `use_reranker` 归位 | 从 `RAGPipeline` 移到检索层——它不是「没实现的参数」，是**放错了层** |

#### 为什么这两种检索能互补

| | 向量（稠密） | BM25（稀疏） |
| --- | --- | --- |
| 强项 | 同义改写、语义相近 | 专有名词、编号、代码标识符 |
| 弱项 | 罕见词被「平均」掉 | 换个说法就零分（无字面重叠 = 0） |

两者的**失败集合交集不大**，所以取并集再重排能吃到两边长处。融合用 RRF：

```
RRF(d) = Σ_channel  w_channel / (k + rank_channel(d))        k 常取 60
```

为什么不用「加权分数和」：归一化后的余弦 ∈ [-1,1]，BM25 分数无上界，
直接相加会被量纲大的一方支配。RRF 只看名次，跨模型、跨语料不需要重新调参。
代价是**丢掉了分数差距信息**——所以它适合融合（求稳），精排交给 Cross-Encoder。

#### (a) 第一套口径：关键词命中（沿用 S2/S3 的判定）

`eval/questions.json` 里每题带 `expected_keywords`，判定方式是「召回块里是否出现任一关键词」。

| 检索策略 | Hit@1 | Hit@4 | MRR | 平均延迟 |
| --- | --- | --- | --- | --- |
| `vector`（S3 基线） | 0.6000 | 0.7000 | 0.6417 | 10.8 ms |
| `bm25` | 0.6500 | **0.9000** | **0.7667** | **1.9 ms** |
| `hybrid`（RRF k=60, cand=50） | **0.7000** | 0.8000 | 0.7375 | 14.8 ms |
| `hybrid` + `rerank` | **0.7000** | **0.9000** | 0.7792 | 639.4 ms |

到这一步，很容易写下这样的结论：「**BM25 单独用就吊打向量检索**（Hit@4 0.90 vs 0.70），
混合检索和精排都是多余的」。我当时差点就这么写了。

#### (b) 转折：这个结论是判定口径的产物

往下翻日志时发现不对。四个被判 MISS 的题，top1 长这样：

| 题 | 期望关键词 | 实际 top1 是什么 | 判定 |
| --- | --- | --- | --- |
| q10 什么是正则化，它有什么用 | `正则化项` | 「第 3 周-**正则化**(Regularization) 112 但若 λ 的值太大了…」 | MISS |
| q11 逻辑回归的代价函数怎么推导 | `对数似然` | 「6.4 **代价函数** 参考视频…」 | MISS |
| q01 梯度下降的更新公式是什么 | `更新公式` | 「…梯度下降所做的就是反复执行这些**更新**」 | MISS |

**这些块明显是相关的**，只是没有把关键词原样写出来。
也就是说判定函数产生了**假阴性**，而且这个偏差有方向性：

> 判定函数 = 字面匹配 ⟹ 字面匹配强的检索方法被系统性偏袒。
> 而 BM25 的优化目标**正是**字面匹配。
> 拿关键词命中率比较「向量 vs BM25」，等于用 BM25 的评分函数当裁判。

于是加了第二套口径：`--judge`，让 LLM 判断「这块材料能否为回答问题提供有用信息」
（不看用词，只看内容）。判定结果写入 `results/judge_cache.json`，带 prompt 版本号，
保证可复现。

| 检索策略 | Hit@1 | Hit@4 | MRR | 平均延迟 |
| --- | --- | --- | --- | --- |
| `vector` | 0.9000 | 1.0000 | 0.9417 | 12.2 ms |
| `bm25` | 0.9000 | 1.0000 | 0.9500 | 2.0 ms |
| `hybrid` | 0.9000 | 1.0000 | 0.9375 | 16.1 ms |
| `hybrid` + `rerank` | **1.0000** | 1.0000 | **1.0000** | 643.3 ms |

**结论完全反转**：

1. `vector` 的 Hit@1 从 **0.60 涨到 0.90** —— 关键词口径把它低估了整整 0.30。
   「BM25 吊打向量」是假象，两者的真实差距在 Hit@1 上是 **0**。
2. 四种策略的 **Hit@4 全是 1.0000** —— 指标**饱和**了。这说明在「20 题 / 1857 块」这个
   难度上，**检索根本不是我当前系统的瓶颈**：前 4 名里总能捞到相关内容。
   真正还有区分度的只剩 Hit@1 和 MRR。
3. **只有精排是稳健的赢家**：两套口径下 MRR 都最高（0.7792 / 1.0000），
   语义口径下 Hit@1 达到 1.0000。代价是 **643 ms**，比 hybrid 慢 **40 倍**。

**为什么精排能赢**：Cross-Encoder 把 `[query, doc]` 拼成一个序列过模型，
query 的每个 token 都能直接看 doc 的每个 token；而向量检索是两边**各自独立**编码后
比一个整体方向，token 级细节早就在池化时丢了。**这就是「召回用 Bi、精排用 Cross」的原因**：
一个可预计算（快、粗、可扩展），一个要逐对前向（慢、准、候选数必须小）。

#### (c) 参数敏感性：全是噪声，别当真

三组参数扫描（其余固定，`--top-k 4`，关键词口径）：

| 参数 | 取值 | Hit@1 | Hit@4 | MRR |
| --- | --- | --- | --- | --- |
| `RRF k` | 10 / 60 / 200 | 0.70 / 0.70 / 0.70 | 0.85 / 0.80 / 0.80 | 0.7500 / 0.7375 / 0.7375 |
| 权重 `v,bm25` | `1,2` / `1,3` / `2,1` | 0.75 / 0.75 / 0.65 | 0.80 / 0.80 / 0.75 | 0.7667 / 0.7750 / 0.7000 |
| `candidate_k` | 10 / 50 / 100 | 0.70 / 0.70 / 0.70 | 0.85 / 0.80 / 0.80 | 0.7542 / 0.7375 / 0.7375 |

看起来「k=10 最好」「权重 1,3 最好」——**但这全是幻觉**：

- 20 题里 **1 题 = 0.05**。0.80 → 0.85 只是**一题之差**。
- 这个样本量下，单题翻转的概率极高，参数排名在不同 prompt / 不同判定器下就会变。
- 所以：**这些参数只有方向性参考价值，具体数值不能写进结论，更不能拿去当默认值炫耀。**
  要定参必须先把评测集扩到 50+ 题并做交叉验证（S5）。

**唯一可信的结论是方向性的**：同一通道质量差距大时，等权融合会拖累强通道
（`v,bm25 = 2,1` 明显最差，因为它压低了表现更好的 BM25）；
`candidate_k` 调大并没有改善，说明「候选池越大越好」是错的直觉——
两路都勉强命中的「弱共识」块反而会挤掉单路强命中的块。

#### (d) 延迟分解（与判定口径无关的硬事实）

| 环节 | 耗时 | 说明 |
| --- | --- | --- |
| BM25 检索 | **1.9 ms** | 只遍历 query 词的倒排链，不扫全库，也不需要 embedding 前向 |
| 向量检索 | 10.8 ms | 其中绝大部分是 **embedding 模型前向**，FAISS 查询本身 < 1 ms |
| RRF 融合 | +1~4 ms | 只是排序和查表，开销可忽略 |
| Cross-Encoder 精排（50 候选） | +625 ms | 50 个 (query, 384 token) 对逐个过 base 模型 |

**这条数据是 S4 唯一不受判定口径影响的结论**：BM25 在**延迟**上的优势是真实的
（5.7 倍），因为稀疏检索不需要神经前向；精排在**精度**上的优势也是真实的，
代价是 40 倍延迟。**选型取决于你的延迟预算，而不是「哪个更先进」。**

#### 踩坑：CrossEncoder 的「二次 sigmoid」

第一版 `reranker.score()` 里，我拿到 `model.predict()` 的返回值又做了一次 sigmoid，
理由是「logit 要压到 0~1」。结果无关文档的分数全是 **0.5000**：

```
第一次: 0.7302 / 0.5000 / 0.5001     ← 错：二次 sigmoid
修正后: 0.9955 / 0.0001 / 0.0003     ← 对
```

原因：`sentence-transformers` 的 `CrossEncoder.predict()` **默认已经应用了模型自带的
激活函数**（bge-reranker 是 Sigmoid），返回的已经是概率。

更隐蔽的危害不是数值偏移，而是**排序信息被压平**：
原本 0.0001 vs 0.0003 的差距，二次 sigmoid 后变成 0.50000 vs 0.50005，
几乎不可分——**分数看着都差不多，但顺序已经乱了**。

> 同类教训：**任何「把输出再变换一次」的代码，先打印原始返回值看分布**，
> 不要凭「它应该是 logit」的想象动手。

#### 这一轮真正的收获

排序一下，哪条最有价值：

1. **判定器比算法更影响结论**。同一批检索结果，换个判定器，`vector` 的 Hit@1 从 0.60 跳到 0.90，
   而算法之间的差距几乎消失。**没有标注就没有评测，没有两套口径就没有可信的评测。**
2. **指标饱和是个信号，不是好消息**。Hit@4 全员 1.00 意味着评测集失去了区分能力，
   下一步该做的是**加难度**（同领域干扰、跨文档多跳），而不是继续调参。
3. **负面/中性结果同样是结论**。混合检索没有在 Hit@1 上打败纯向量，这件事本身值得写下来。
4. 在 20 题的样本量上，任何「调参提升 1 题」都不可信——**先问样本量，再问显著性**。

### 实验 8 · 50 题分层评测集 + 生成层指标（S5）

#### 为什么先换尺子

S4 的结论是：20 题 / 1857 块，语义口径下四策略 Hit@4 全是 1.00 —— **评测集已经饱和**。
在这个尺子上继续调参，看到的只会是噪声。所以 S5 的第一件事不是改代码，是**换一个还能量出差异的尺子**。

`eval/questions_v2.json` 按「检索难点」而不是按文档分四层：

| 层 | n | 测什么 | 指标 | 关键词指标为什么不够 |
| --- | --- | --- | --- | --- |
| `single_fact` | 20 | 基本召回 | Hit@1 / Hit@4 / MRR | 够用 |
| `distractor` | 15 | 术语跨文档出现，但只有一本给答案 | **来源命中率** | 关键词命中不区分「捞对了」和「捞到同名的另一本书」 |
| `multi_hop` | 8 | 必须同时拿到两份文档 | **来源覆盖率** | 关键词命中一块就满分，看不到「缺一半」 |
| `no_answer` | 7 | 语料里没有这个知识 | 交给生成层测拒答 | 关键词无从判定，且「捞到相似内容」不算错 |

每题字段与判定口径见文件头的 `_说明`。`scripts/check_questions.py` 做静态自检，
它查的是**写题库时最容易犯的错**：标注的来源里其实没有答案。

```
$ python scripts/check_questions.py
s01   single_fact  pumpkin-book=8 ml-notes-ng=1   OK 标注来源 8 块
...
n01   no_answer    -                              OK（语料确实没有）
共 50 题，问题题号：无
```

> 自检还抓到一个真实问题：静态检查要求关键词落在**正文块**（排除含 `....` 的目录页）。
> PDF 目录会把所有章节标题聚在一起，含关键词但没有答案，是检索评测里的典型**高分噪声**。

#### 新指标怎么定义

生成层不只看「答没答对」，看三件可机械验证的事：

| 指标 | 计算 | 说明 |
| --- | --- | --- |
| 引用覆盖率 | 有 ≥1 个合法引用的答案 / 作答数 | 愿不愿意标来源 |
| 引用合法率 | 合法引用 / 全部引用 | 标了但页码不在召回里 = 编造 |
| 忠实度 | 被资料支持的断言数 / 断言总数 | 一次 LLM 调用拆 claims，不是逐句调用（省 50 倍成本） |
| 无答案题拒答率 | 正确拒答 / 7 | 语料没有的，必须拒 |
| 过度拒答率 | 有答案题被拒 / 43 | 该答不答，同样不可接受 |

**引用校验刻意不用 LLM**：`[来源: 文件 第N页]` 是否对应本次召回块，是确定性问题。
用模型判断只会引入不确定性，而且不可复现。

#### E8-1 分层检索（hybrid，top_k=4）

| 层 | 结果 |
| --- | --- |
| 35 道可回答题 | Hit@1 **0.7429**(26/35) · Hit@4 **0.8857**(31/35) · MRR **0.8095** |
| 15 道干扰题 | 来源命中 @4 = **1.0000** · @1 = **1.0000** |
| 8 道多跳题 | 来源覆盖率 **0.6250** · 全覆盖率 **0.2500**(2/8) |
| 7 道无答案题 | 不计入检索指标 |

**注意**：这组数字与 v1 的 0.600/0.700 **不可比** —— 题目换了，口径也变了。
横向比较只能在同一个题库内做。

干扰题 @1 = 100% 是个**负面结果**：这 15 题没有区分力。
原因是三本书主题重叠度太低（一本 ML 公式推导、一本 ML 课程笔记、一本 LLM 应用），
「同领域干扰」只在两本 ML 书之间存在，而术语分布又极度倾斜（如「正则化」32 : 8）。
要造出真正的干扰，需要**同主题的多个版本文档**（如同一本书的不同译本、不同年份的课程讲义），
靠改题目描述造不出来。

#### E8-2 多跳的瓶颈是召回预算，不是排序质量

| top_k | Hit@1 | Hit@k | 多跳覆盖率 | 多跳全覆盖 |
| --- | --- | --- | --- | --- |
| 4 | 0.7429 | 0.8857 | 0.6250 | 0.2500 (2/8) |
| 8 | 0.7429 | **1.0000** | 0.8125 | 0.6250 (5/8) |
| 12 | 0.7429 | 1.0000 | **0.9375** | **0.8750** (7/8) |

**Hit@1 三个 k 完全不动**（0.7429）—— 排序质量没变，变的是「给几个槽位」。
多跳题缺的不是更好的排序，是**预算**。这条对工程配置的直接含义：
多跳类问题应该用更大的 `top_k`（或按题目类型动态取 k），而不是换更大的模型。

> 数据：`results/eval_v2_hybrid.json` / `eval_v2_hybrid_k8.json` / `eval_v2_hybrid_k12.json`（三份都可复跑）。

#### E8-3 prompt 消融：引用和拒答到底是谁带来的

同 50 题、同检索配置（hybrid / top_k=4），只改 prompt：

| 配置 | 作答 | 引用覆盖 | 引用合法 | 编造引用的答案 | 忠实度 | 无答案拒答 | 过度拒答 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `full`（正式） | 33 | **1.000** | **1.000**(108/108) | 0 | 0.9949 | **7/7** | 0.2326 |
| `no_refusal`（去掉拒答条款） | 38 | 1.000 | 0.9781(134/137) | 1 | 0.9962 | **7/7** | **0.1163** |
| `no_cite`（去掉引用要求） | 32 | **0.000** | — | 0 | 0.9896 | 7/7 | 0.2558 |

三条结论：

1. **引用是 prompt 造出来的行为**。去掉引用要求，覆盖率从 100% 直接掉到 0 ——
   模型**不会自发**标注来源。反过来说，「有引用」这件事只能靠工程约束保证，不能靠模型自觉。
2. **拒答不是哨兵条款带来的**。去掉「资料不足输出 INSUFFICIENT_CONTEXT」后，
   无答案题仍然 7/7 拒答。真正的约束是 prompt 开头那句「只能依据资料回答」。
   **根约束和输出格式是两件事，别把功劳记在后者的账上。**
3. **哨兵条款的唯一实测效果是把过度拒答翻倍**（11.6% → 23.3%）。
   它没有提高「该拒就拒」，只提高了「不该拒也拒」。

   → 工程建议：拒答信号用**自然语言 + 独立检测器**即可（本项目的
   `refusal_state()` 就是），哨兵只在对下游系统需要严格机器可读时才有必要，
   并且要接受它带来的过度拒答代价。

> 数据：`results/gen_eval_full.json` / `gen_eval_no_refusal.json` / `gen_eval_no_cite.json`。

#### E8-4 检索预算会一路传导到生成层

| 配置 | 作答 | 多跳题作答 | 过度拒答 | 引用条数 | 忠实度 | 平均生成延迟 |
| --- | --- | --- | --- | --- | --- | --- |
| top_k=4 | 33/43 | 2/8 | 23.3% | 108（全合法） | 0.9949 | 1414 ms |
| top_k=12 | 36/43 | 5/8 | **16.3%** | 152（全合法） | 1.0000 | 1534 ms |

`top_k` 从 4 到 12：多跳作答 2→5、过度拒答 23.3%→16.3%、延迟只涨 8.5%。
**「模型不敢答」有一部分根本不是模型的问题，是检索没给到。**
这也是为什么「先测检索、再怀疑模型」必须成为习惯而不是口号。

#### 这一轮踩的坑（三条都是关于「度量工具」）

1. **拒答判定器自己坏了**。第一版只要答案里出现「无法确定」就算拒答，
   结果把一条 169 字的正常答案判成拒答（正文恰好写了这四个字），
   50 题里 12 题判定分歧。改成「看位置 + 看长度」后分歧降到 1~2 题。
   **教训：度量工具本身也要被验证，否则它会把「答案不完整」错记成「不敢答」。**
2. **忠实度指标饱和**。三种 prompt 配置下 0.9896 ~ 1.0000，没有区分力。
   原因是它只问「说的有没有依据」，不问「该说的说了没有」——
   拒答和极短答案天然拿满分。**要测完整性必须引入参考答案**，那是另一个成本量级的事。
3. **引用合法 ≠ 引用恰当**。当前只验证「这个文件的这一页在召回结果里」，
   没有验证「这一页真的支撑了这句话」。前者能挡住编造页码，挡不住**张冠李戴**。

## 已知限制 / 待办

- [ ] 中文友好分隔符的收益**尚未单独度量**（与解析器修复捆绑在基线之前，见实验 4 备注）
- [ ] 页眉页脚类**重复样板文本**未处理（如南瓜书每页都印的书名推广语会污染检索），
      可用「跨页高频行」规则过滤
- [ ] **增量索引只增不删**：删掉某个 PDF 后它的 chunk 仍留在库里（FAISS 不支持按文档删除），
      需要 `--recreate` 才能彻底清除。要做真正的删除得引入 ID 映射 + 重建或换支持删除的库
- [ ] 索引参数（`M` / `efSearch` / `nlist` / `nprobe`）没有在**真实大规模语料**上调优——
      当前语料只有 1857 块，规模实验用的是复制加噪的合成规模
- [ ] 未做向量量化（PQ）与内存占用对比；ANN 的另一半代价（内存）还没有量化
- [ ] ~~评测集只有 20 题、语义判定下 Hit@4 已饱和~~ → S5 已扩到 50 题分层，
      但**忠实度仍然饱和**（0.99~1.00），且干扰题来源命中 @1=100% 毫无区分力（实验 8）
- [ ] **答案正确性（correctness）没测**。忠实度只问「是否被资料支撑」，
      资料错了答案可以「忠实但错误」。要测正确性必须有参考答案，标注成本另算
- [ ] **引用只验证页码存在，不验证支撑关系**。「合法引用」挡得住编造页码，
      挡不住张冠李戴（把 A 结论标到讲 B 的页上）
- [ ] 多跳只有 8 题、无答案只有 7 题，样本量太小，**比例数字只能看方向**；
      no_answer 的负例偏「完全不相关」（FlashAttention / SimCLR），
      缺「语料有相邻概念但确实没这条」的难题，因此 7/7 的拒答率偏乐观
- [ ] 没有参考答案 → 无法计算 completeness / recall of key points，
      模型「只说一半但不出错」会被判成满分
- [ ] LLM-as-Judge 自身没有校准：没测过它的位置偏差、长度偏差、以及「同一输入是否稳定」。
      当前只做到「temperature=0 + 缓存 + 每次保存判定理由便于抽查」
- [ ] 词表级歧义没有处理：q02 问「线性判别分析 LDA」时，检索命中的是「LDA 主题模型」，
      judge 也被这个词骗了判为相关。这类**语料级同形异义**只能靠人工标注发现
- [ ] 精排只对融合结果做，没有尝试「直接对 BM25 候选精排」或「省掉融合只做精排」
- [ ] **前端没有鉴权、没有并发控制、没有 trace 落盘**：只适合本机单人使用。
      要做成多人可用的服务，至少还需要请求限流、会话隔离、以及「每次问答的检索块 + prompt + 引用」留痕
- [ ] 前端不做答案正确性校验（与评测口径一致：只校验引用页码是否在召回内），
      **页面好看不等于答案对**

## 演进路线

按「**一阶段只改一个变量**，改完用固定问题集对比、把指标写进文档」的方式推进：

| 阶段 | 目标 | 状态 |
| --- | --- | --- |
| S0 | 工程清理：去掉死代码与悬空配置，让依赖可信 | 已完成 |
| S1 | 替换为中文 embedding 模型 | 已完成 |
| S2 | 切分策略对照实验（中文 token 上限 / 解析器选型 / 段落规整） | 已完成 |
| S3 | 向量库工程化：FAISS 索引 + L2 归一化 + 阈值分层 + 增量索引/去重 | 已完成 |
| S4 | 混合检索（BM25）+ RRF 融合 + Cross-Encoder 精排 + 第二套判定口径 | 已完成 |
| S5 | 50 题分层评测集 + 生成层指标（引用 / 忠实度 / 拒答）+ prompt 模板化与消融 | 已完成 |
| S6 | Query 改写 / 父子块 / 服务化 | 进行中：服务化（FastAPI + SSE + 前端）已完成 |
